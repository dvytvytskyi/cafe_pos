## 1. Швидкий список багів і правок

### 1.1. Друк замовлення (Print order)

**Де:** вкладка з деталями замовлення + вікно «Create Order».

**Проблема:** немає загальної кнопки друку; замовлення має йти **окремо на кухню і на бар**.

**Потрібно:**
- Кнопка **«Print order»** (загальна) у деталях замовлення.
- Окремий чек **на бар** (напої).
- Окремий чек **на кухню** (їжа).
- Те саме в вікні **«Create Order»** — можливість надрукувати перед/після створення.

**Критерій готовності:**
- [ ] Одна кнопка «Print order» з маршрутизацією по станціях (kitchen / bar).
- [ ] Друк працює і з деталей замовлення, і з Create Order.

---

### 1.2. Checkout — калькулятор здачі

**Проблема:** після натискання Checkout і вибору Cash або Card **нічого не відбувається**.

**Очікувана поведінка:** з’являється екран/модалка типу **калькулятора**:
- скільки гість платить (введення суми);
- скільки дати **здачі** (автоматичний розрахунок).

**Критерій готовності:**
- [ ] Після Checkout → Cash відкривається payment sheet з полем «Отримано» і «Здача».
- [ ] Card — відповідний flow оплати карткою.
- [ ] Після підтвердження замовлення закривається / оновлюється статус.

---

### 1.3. Refund Items — кількість позицій

**Проблема:** на екрані Refund Items **відсутні стрілочки або + / −** для зміни кількості блюд при поверненні.

**Потрібно:**
- Stepper (+ / −) або стрілки для кожної позиції refund.
- Можливість повернути частину кількості (напр. 1 з 2).

**Критерій готовності:**
- [ ] Кожна позиція має контрол кількості для refund.
- [ ] Сума refund перераховується при зміні кількості.

---

### 1.4. Генерація фактури — відправка на email

**Проблема:** відсутня функція **надсилання фактури на пошту** гостю.

**Потрібно:**
- Генерація фактури (invoice).
- Поле email + кнопка «Надіслати» / автоматична відправка після закриття чека.

**Критерій готовності:**
- [ ] Можна згенерувати invoice для замовлення.
- [ ] Можна вказати email і надіслати фактуру.

---

### 1.5. Ручне додавання позицій офіціантом

**Проблема:** офіціант **не може вручну додати позицію з меню** до існуючого замовлення.

**Потрібно:**
- Кнопка «Add item» / пошук по меню в деталях замовлення.
- Вибір модифікаторів (extras) при додаванні.

**Критерій готовності:**
- [ ] З деталей замовлення можна відкрити меню і додати позицію.
- [ ] Позиція з’являється в замовленні з правильною ціною.

---

### 1.6. Split amount — розділення позицій

**Проблема:** функція split **не розділяє позиції**.  
Приклад: 2 гості замовили по однаковій позиції — неможливо розділити, щоб один платив 25 €, інший 25 €.

**Потрібно:**
- Split по **позиціях** (assign item → guest / check).
- Split по **сумі** між кількома гостями.
- Можливість оплатити одну частину cash, іншу card (див. [§2.1](#21-розділення-замовлення)).

**Критерій готовності:**
- [ ] Можна призначити кожну позицію окремому гостю / частині рахунку.
- [ ] Дві однакові позиції можна рознести на двох платників.
- [ ] Різні способи оплати для різних частин.

---

### 1.7. Discount — сума, не тільки %

**Проблема:** дисконт тільки у **відсотках**.

**Потрібно:**
- Дисконт **по сумі** (як у tips) — фіксована сума знижки.
- Опційно залишити % як альтернативу.

**Критерій готовності:**
- [ ] Можна ввести знижку в € (або локальній валюті).
- [ ] Можна ввести знижку в %.
- [ ] Підсумок замовлення перераховується коректно.

---

### 1.8. Редагування замовлення (модифікатори)

**Проблема:** неможливо **змінити** вже додану позицію.

**Приклад:** гість замовив авокадо тост з **екстра соусом A**, передумав — потрібен **екстра соус B**.

**Потрібно:**
- Редагування позиції в замовленні: модифікатори, кількість, нотатки.
- Перерахунок ціни після зміни.

**Критерій готовності:**
- [ ] Tap на позицію → edit mode (modifiers, qty, notes).
- [ ] Зміна соусу A → B оновлює line item і total.

---

### 1.9. Dine-In фільтр — зайва колонка

**Проблема:** у фільтрі **Dine-In** є колонка **«Ready for Pick Up»**, яка там не повинна бути.

**Потрібно:**
- Прибрати або приховати колонку Ready for Pick Up для dine-in flow.
- Колонка лишається тільки для takeaway / pickup (якщо застосовно).

**Критерій готовності:**
- [ ] Dine-In board не показує «Ready for Pick Up».
- [ ] Pickup/takeaway board показує відповідні колонки.

---

### 1.10. Delivery — автоматично оплачені

**Проблема:** замовлення на **доставку** мають йти в CRM як **вже оплачені**.

**Потрібно:**
- Статус оплати: **paid** при створенні / імпорті delivery-замовлення.
- **Немає** Checkout, Split, Refund UI для таких замовлень (або обмежений набір дій).
- Відображення в orders board як paid order.

**Критерій готовності:**
- [ ] Delivery orders створюються з `paymentStatus: paid`.
- [ ] Немає кнопки Checkout для delivery.
- [ ] У CRM видно, що замовлення оплачене зовні (aggregator / prepay).

---

### 1.11. Loyalty points — використання з боку офіціанта

**Проблема:** якщо у гостя є **накопичені points**, офіціант **не бачить** способу їх застосувати.

**Потрібно:**
- Пошук / прив’язка гостя до замовлення (телефон, QR, loyalty card).
- Застосування points як **знижка** (частково або повністю).
- Відображення балансу points перед checkout.

**Критерій готовності:**
- [ ] В деталях замовлення видно баланс loyalty гостя.
- [ ] Можна списати points (full / partial payment).
- [ ] Сума до оплати зменшується відповідно до rules програми.

## 2. Робота з замовленням і чеком

### 2.1. Розділення замовлення

- Можливість відмічати як **винесені** окремі позиції, а не тільки весь заказ цілком.
- Можливість **розділити рахунок** на кілька частин.
- При розділенні: одна частина **готівкою**, інша **карткою**.

**Критерій готовності:**
- [ ] Mark-as-served per line item.
- [ ] Split bill на N частин.
- [ ] Різний payment method на кожну частину.

---

### 2.2. Додавання позицій до існуючого замовлення (друк)

- При додаванні нових позицій до вже існуючого замовлення на друк йдуть **тільки нові** позиції.
- Раніше відправлені позиції **не друкуються повторно** (kitchen ticket / bar ticket).

**Критерій готовності:**
- [ ] Кожна line item має прапорець `sentToKitchen` / `sentToBar`.
- [ ] Print після add items друкує лише unsent lines.
- [ ] Повторний print всього замовлення — окрема дія (якщо потрібна).

---

### 2.3. Кількість гостей

- Перед підтвердженням замовлення **обов’язково** вказувати кількість гостей за столом.
- Після вказання кількості гостей — **вибір співробітника**, який прийняв замовлення.

**Критерій готовності:**
- [ ] Modal/step: guest count (required).
- [ ] Modal/step: select staff who took the order (required).
- [ ] Дані зберігаються в order / table session.

---

### 2.4. Відповідальний за замовлення і оплату

- Можливість **закріпити офіціанта** за столом (обслуговує).
- **Закриття чека** можливе лише після вибору співробітника, який приймає оплату.
- У системі завжди видно:
  - хто **прийняв** замовлення;
  - хто **обслуговує** стіл;
  - хто **закрив чек** / прийняв оплату.

**Критерій готовності:**
- [ ] Table → assigned waiter (server).
- [ ] Order → `takenByStaffId`, `servedByStaffId`, `closedByStaffId`.
- [ ] Checkout blocked until `closedByStaffId` selected.
- [ ] UI показує всі три ролі в деталях замовлення.

## 3. Облік продажів по кожному офіціанту

Потрібна можливість відстежувати продажі кожного офіціанта і розуміти, який співробітник відповідає за обслуговування столу.

### 3.1. Функціонал

- Закріплення офіціанта за конкретним столом.
- Відображення співробітника, який **прийняв** замовлення.
- Відображення співробітника, який **закрив чек**.
- Визначення, хто **продав** кожну позицію (страва / напій).

### 3.2. Альтернативний варіант

Якщо технічно неможливо автоматично закріплювати всі продажі за офіціантом — при додаванні додаткових напоїв, десертів і інших позицій співробітник **обирає своє ім’я**.

### 3.3. Звіти

Звіт по кожному офіціанту:

| Показник | Опис |
|----------|------|
| Кількість проданих позицій | units |
| Загальна сума продажів | revenue |
| Кількість замовлень / чеків | order count |
| Розбивка по категоріях | optional |

**Мета:** розуміти, хто активно продає; порівнювати ефективність; виявляти потребу в навчанні.

**Критерій готовності:**
- [ ] `lineItem.soldByStaffId` або аналог.
- [ ] Звіт Waiter Sales у CRM / reports.
- [ ] Фільтр по локації, зміні, даті.

## 4. Gift Card і сертифікати

Розділ для обліку подарункових карт і сертифікатів, які гості використовують для оплати.

### 4.1. Основний функціонал

- Єдина база Gift Card і сертифікатів.
- Створення нового сертифіката.
- Унікальний **номер / код** на сертифікат.
- Статус: активний / використаний.
- Оплата замовлення Gift Card або сертифікатом при закритті чека.

### 4.2. Синхронізація між локаціями

- Єдина база для всіх локацій.
- Кожна локація працює під своїм доступом.
- При використанні сертифіката статус **одразу оновлюється** у всіх локаціях.
- Всі локації бачать актуальний статус: **активний / використаний**.

### 4.3. Контроль повторного використання

- Система **не дозволяє** повторно використати погашений сертифікат або Gift Card.
- Мета: виключити використання одного сертифіката в різних локалях; коректний облік способу оплати.

**Критерій готовності:**
- [ ] CRUD сертифікатів у CRM.
- [ ] Payment method «Gift Card» на checkout.
- [ ] Redeem API з idempotency / lock.
- [ ] Cross-location sync (realtime або polling).

## 5. Аналітика кухні та бару

Окремий розділ аналітики для контролю **швидкості приготування** замовлень.

### 5.1. Загальні показники

- Середній час від статусу **«Aceptar»** до **«Hecho»**.
- Середній час приготування замовлення (end-to-end).

### 5.2. Кухня

| Метрика | Опис |
|---------|------|
| Середній час кухні | kitchen station |
| Середній час по кожній страві | per menu item |
| Найдовші страви | top slow items |
| Найшвидші страви | top fast items |

### 5.3. Бар

| Метрика | Опис |
|---------|------|
| Середній час бару | bar station |
| Середній час по кожному напою | per drink |
| Найдовші напої | top slow |
| Найшвидші напої | top fast |

### 5.4. Фільтри (бажано)

- Конкретна позиція меню.
- Співробітник (хто готував, якщо є дані).
- Зміна.
- Локація.

**Мета:** розуміти, де затримки; які позиції створюють навантаження на кухню / бар.

**Критерій готовності:**
- [ ] Timestamps на line items: `acceptedAt`, `readyAt`, `station` (kitchen/bar).
- [ ] Dashboard Kitchen & Bar Analytics у CRM.
- [ ] Експорт / період date range.
